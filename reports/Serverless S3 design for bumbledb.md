# Commit to Express, checkpoint to Standard

Turso made SQLite fast as a hosted database with three moves. It kept **one writer per database**. It ran every query against a local file. And it moved the commit point into **S3 Express One Zone**: a commit is acknowledged only after its WAL bytes land in Express, where a 4 KB PUT averages **6.4 ms with a 7 ms p99**. Frequent checkpoints then fold the WAL into 128 KB segments on S3 Standard, and local NVMe is only a cache. bumbledb's proposed create-only log is the right skeleton for the same result. Delta Lake, Graft and SlateDB all converged on this commit protocol. It cuts today's three serial round trips to one, and its byte-compare ownership check makes retries and hedged PUTs safe. Four changes make it Turso-fast and keep it correct. First, put `log/` in an Express directory bucket and `ckpt/` in a Standard bucket, because Express LIST results are not in lexicographic order, so the proposal's `LIST max-keys=1` checkpoint lookup returns the wrong key there. Second, skip the catch-up GET on a warm instance, because the conditional PUT already checks freshness. Third, batch whatever arrives while a PUT is in flight into one `Commands` entry, with at most one PUT in flight per process. Fourth, store the decided row effects and a per-submission nonce in every entry, so catch-up never re-judges and byte comparison cannot confuse two clients' identical commands. With these changes, a warm, uncontended submit costs one Express PUT of about 7 ms. By my estimate, today's submit averages roughly 60–90 ms on S3 Standard. A cold start costs a checkpoint download plus a bounded, parallel tail probe, which I estimate at 100–200 ms for a database of about 10 MB. Epochs and leases add no safety when the only commit point is a create-only key. Never deleting log objects closes the stale-writer re-create hole for v1. Freeze/Migration/Thaw entries give migrations the atomic read-decide-record step that Drizzle lacks, provided Freeze carries a deadline and a failed migration is recorded as sticky.

## Turso got fast by moving the commit point into S3 Express

"Turso" names three different systems depending on the date. From 2022 to 2024 it was the open-source libSQL server (sqld), a Rust process wrapping a C fork of SQLite and hosted on small Fly.io VMs. From late 2024 it was a new closed-source, massively multi-tenant server on AWS that went "diskless" in 2025 ([Turso roadmap, 2025-01-21](https://turso.tech/blog/upcoming-changes-to-the-turso-platform-and-roadmap)). Since December 2024 it has also been "Turso Database", a Rust rewrite of SQLite. Supabase announced on 2026-10-02 that it is acquiring Turso, and the engine remains MIT-licensed ([Turso is joining Supabase](https://turso.tech/blog/turso-is-joining-supabase)). Each era fixed a specific failure of the one before it, and those failures are the most useful evidence for bumbledb.

### sqld kept one writer per database and proxied every write to it

sqld is a single-writer design on stock SQLite semantics. One **primary** per database accepts writes and keeps a replication log of WAL frames. **Replicas** run reads locally and delegate any write, or any transaction that becomes a write, to the primary over a gRPC stream ([libsql USER_GUIDE](https://github.com/tursodatabase/libsql/blob/main/docs/USER_GUIDE.md)). Delegation ships a whole transaction as one `Program` of conditional steps. The reply carries the primary's `current_frame_no` after execution ([proxy.proto](https://github.com/tursodatabase/libsql/blob/main/libsql-replication/proto/proxy.proto)). The replica records that frame number and blocks later reads on the same connection until its replicator has applied it. That gives read-your-writes without a full sync ([write_proxy.rs](https://github.com/tursodatabase/libsql/blob/main/libsql-server/src/connection/write_proxy.rs)). A replica that has just started and is behind the primary proxies every request to the primary until it catches up, so a cold replica never serves stale data ([write_proxy.rs](https://github.com/tursodatabase/libsql/blob/main/libsql-server/src/connection/write_proxy.rs)). Operations on the primary are linearizable. Replica reads are monotonic but have no global order ([CONSISTENCY_MODEL.md](https://github.com/tursodatabase/libsql/blob/main/docs/CONSISTENCY_MODEL.md)).

Multi-tenancy came from **namespaces**: many SQLite files in one process, selected by an `x-namespace` header or a Host subdomain ([db_factory.rs](https://github.com/tursodatabase/libsql/blob/main/libsql-server/src/http/user/db_factory.rs)). Each customer got a small VM that scaled to zero when idle ([Glauber Costa, 2024-10-16](https://turso.tech/blog/a-deep-look-into-our-new-massive-multitenant-architecture)). That server broke under load. A customer created about 5,000 databases in a few hours and triggered a Tokio deadlock that "took us weeks" to find. Turso rewrote the server as a hand-written sync-Rust event loop under deterministic simulation testing. On a local HTTP query, the mean dropped from **20.4 ms to 3.3 ms** ([same post](https://turso.tech/blog/a-deep-look-into-our-new-massive-multitenant-architecture)). The new server is closed source but speaks the same protocols ([roadmap](https://turso.tech/blog/upcoming-changes-to-the-turso-platform-and-roadmap)).

### Page-shipping replicas proved wasteful and fragile

libSQL replication is physical log shipping. Each frame is a 24-byte header plus one 4 KiB page. The header holds an incrementing `frame_no`, a rolling CRC-64, the page number, and the database size after commit, which marks the transaction boundary ([frame.rs](https://github.com/tursodatabase/libsql/blob/main/libsql-replication/src/frame.rs)). A replica handshakes to learn the **generation**, a UUID that changes on every primary restart, and then streams frames from its last applied position. When the log has been compacted past that position, the server answers `NEED_SNAPSHOT`. The replica then pulls a snapshot holding the newest version of each page ([replication_log.proto](https://github.com/tursodatabase/libsql/blob/main/libsql-replication/proto/replication_log.proto), [snapshot.rs](https://github.com/tursodatabase/libsql/blob/main/libsql-server/src/replication/snapshot.rs)).

**Embedded replicas** put that machinery in the client library. The replica is a local SQLite file that pulls frames on `sync()` or on a `syncInterval`. Reads run locally in microseconds. By default, writes go to the cloud primary and are then reflected back ([embedded replica docs](https://docs.turso.tech/features/embedded-replicas/introduction)). A fresh client must download the entire database through `/export/{generation}` before its first query ([sync.rs](https://github.com/tursodatabase/libsql/blob/main/libsql/src/sync.rs)). The docs state that embedded replicas cannot run "in serverless environments without a filesystem", and that a 1-byte row "will always show up as a 4kB write" ([docs](https://docs.turso.tech/features/embedded-replicas/introduction)).

Glauber Costa's 2026 post-mortem is blunt. Physical pages were wasteful and gave "no visibility on what changed". Keeping the cloud and local copies applying pages in the same order across checkpoints "was challenging … the local database often diverged, and had to be re-bootstrapped" ([Turso sync benchmark, 2026-04-24](https://turso.tech/blog/sync-benchmark)). The same post measured the cost over the public internet. A read-your-writes loop took **243 ms per cycle** on embedded replicas and under 1 ms on the logical Turso Sync. Pushing after every write took 218 ms against 30 ms. Bootstrapping 5,000 rows (about 1 MB) took 718 ms against 338 ms.

### Bottomless backed up asynchronously; diskless Turso waits for Express

**bottomless** is libSQL's virtual WAL that copies committed frames to S3 **asynchronously**. It uploads a zstd-compressed batch every **15 s or 10,000 frames**, whichever comes first, and names each object by its frame range. Objects sit under generation prefixes built from a reversed-timestamp UUIDv7, so the newest generation lists first, and a `.dep` object links each generation to its parent. A restore walks those links back to a snapshot and replays WAL batches up to a chosen frame or timestamp, which is how bottomless provides point-in-time recovery ([bottomless replicator.rs](https://github.com/tursodatabase/libsql/blob/main/bottomless/src/replicator.rs)). Its one synchronous guard is that a checkpoint waits until S3 confirms the frames, so the local WAL is never truncated before it is backed up ([bottomless_wal.rs](https://github.com/tursodatabase/libsql/blob/main/bottomless/src/bottomless_wal.rs)). Turso later admitted the cost of acknowledging first: "there was a period when writes were not really durable anywhere except the local disk" ([Turso Cloud goes diskless, 2025-04-07](https://turso.tech/blog/turso-cloud-goes-diskless)).

The diskless redesign, generally available on AWS since 2025-03-17, inverts that order. "Commits are only acknowledged once data is safely stored in either S3 or S3-express. Compute nodes can come and go at any time, and local disks act as a local cache" ([Turso durability docs](https://docs.turso.tech/cloud/durability)). On the write path, a transaction executes in memory. The node then waits a few milliseconds to collect WAL entries from many tenant databases, uploads them in a **single PUT** to Express, acknowledges the transactions, and finally writes the data to local NVMe ([AWS Storage Blog, 2026-07-23](https://aws.amazon.com/blogs/storage/how-turso-built-a-transactional-database-using-amazon-s3-express-one-zone/)). Servers checkpoint "usually after each 1MB written" into **128 kB segments** on S3 Standard, grouped into versioned generations. Failover pulls the latest WAL back from Express and fetches segments lazily ([How Turso Cloud keeps data durable, 2025-05-20](https://turso.tech/blog/how-does-the-turso-cloud-keep-your-data-durable-and-safe)).

Cost forced the batching. Turso's own arithmetic put one-row transactions on a $4.99 plan at $125 per month in Standard PUTs, which was viable only when amortized across about 100 active databases per node ([diskless post](https://turso.tech/blog/turso-cloud-goes-diskless)). The cold-start story changed too. On AWS, "databases never have cold starts … every database is just a SQLite file, and the server itself is always up" ([Turso AWS GA](https://turso.tech/blog/turso-aws-out-of-beta)). Turso has not published how two pods writing the same database are fenced, nor the format of the multi-tenant batch.

### The Rust rewrite bought async I/O and a logical sync engine

Turso Database (formerly Limbo) is still pre-1.0, with **v0.8.2** released 2026-10-06 ([releases](https://github.com/tursodatabase/turso/releases)). Turso gave two reasons for leaving the fork. SQLite's test suite is proprietary and its C codebase made deep changes risky ([Introducing Limbo](https://turso.tech/blog/introducing-limbo-a-complete-rewrite-of-sqlite-in-rust)), and "doing sync right was at the very top of the list" ([sync benchmark](https://turso.tech/blog/sync-benchmark)). The engine does I/O through explicit state machines rather than Rust async/await. Functions return `IOResult::Done(T)` or `IOResult::IO(completions)`, and the caller drives the I/O ([async-io-model.md](https://github.com/tursodatabase/turso/blob/main/docs/agent-guides/async-io-model.md)).

**Turso Sync** (launched 2025-10-08) is deliberately asymmetric. "Local changes are pushed to the remote as logical mutations … Remote changes are pulled as physical pages", and the remote is the source of truth ([Turso Sync launch](https://turso.tech/blog/introducing-databases-anywhere-with-turso-sync)). A pull rolls back unpushed local changes, applies the remote state, and replays the local changes on top, all atomically. Conflicts resolve as "last push wins", with an optional `transform` hook ([conflict resolution docs](https://docs.turso.tech/sync/conflict-resolution)). Pushes are idempotent because the server keeps a `turso_sync_last_change_id(client_id, pull_gen, change_id)` table ([database_sync_operations.rs](https://github.com/tursodatabase/turso/blob/main/sync/engine/src/database_sync_operations.rs)). An experimental partial sync fetches pages lazily when a query touches them, bootstrapping from either a byte prefix or the pages a server-side query reads ([partial sync docs](https://docs.turso.tech/sync/partial)). DDL travels as replayed SQL text, with CREATE rewritten to `IF NOT EXISTS` ([database_sync_operations.rs](https://github.com/tursodatabase/turso/blob/main/sync/engine/src/database_sync_operations.rs)).

### MVCC lifts engine concurrency, not log throughput

`BEGIN CONCURRENT` is Hekaton-inspired optimistic MVCC. Row versions live in an in-memory skip map, write-write conflicts are checked per row at commit, and a commit fsyncs a logical log that "records only the rows a transaction changed" before that log is checkpointed into the B-tree ([Turso group commit post](https://turso.tech/blog/turso-group-commit)). It has been an early preview on Turso Cloud since 2026-08-03. DDL such as CREATE INDEX cannot run inside a concurrent transaction ([Concurrent writes in practice](https://turso.tech/blog/concurrent-writes-in-practice)), and the manual still marks the mode "not production ready" ([Turso manual](https://github.com/tursodatabase/turso/blob/main/docs/manual.md)).

Turso's v0.8 benchmark claims **9,500 TPS at 64 connections versus 1,370 for SQLite**, and a p99.9 commit latency of 2.4 ms against 1.2 s at 32 connections. It also concedes that "SQLite … is faster than Turso with a single connection" ([Turso 0.8](https://turso.tech/blog/turso-0.8.0)). For bumbledb the transferable lesson is the log format, not the concurrency. When every commit is an S3 PUT, the serialization point is the log chain, not the storage engine. Batching commands into each entry raises throughput. A second LMDB writer would not.

### Turso's budget is a 6.4 ms PUT plus a window it sells by plan

| Turso latency fact | Value | Source |
|---|---|---|
| S3 Express 4 KB PUT, same AZ (avg / p95 / p99) | 6.4 / 7 / 7 ms | [Turso diskless](https://turso.tech/blog/turso-cloud-goes-diskless) |
| S3 Express 4 KB PUT, cross-AZ | 7 / 8 / 8 ms | same |
| S3 Standard 4 KB PUT | 31 / 60 / 102 ms | same |
| Local fsync it replaced | ~2 ms | [AWS Storage Blog](https://aws.amazon.com/blogs/storage/how-turso-built-a-transactional-database-using-amazon-s3-express-one-zone/) |
| Added commit-latency ceiling (batch window) | Free 100, Developer 50, Scaler 25, Pro 10 ms | [Durability docs](https://docs.turso.tech/cloud/durability) |
| Cold start on AWS | none; always-on shared process | [Turso AWS GA](https://turso.tech/blog/turso-aws-out-of-beta) |

The window is a ceiling, not an average. A commit that arrives late in the window waits less ([Durability docs](https://docs.turso.tech/cloud/durability)). Turso's commit latency is therefore one Express PUT plus up to 10–100 ms of batching, which Turso sells as a pricing tier. The window amortizes PUT cost across tenants. A single-user database has no tenants to amortize across, so bumbledb can skip the window entirely.

## Drizzle and Expo ship migrations as code with an unlocked ledger

The "migrations ship with the app" model the owner wants comes from Drizzle, and Drizzle's implementation shows as much what to avoid as what to copy. `drizzle-kit generate` writes SQL files: `NNNN_tag.sql` plus `meta/_journal.json` on the stable v0 line, and one `<YYYYMMDDHHMMSS>_<name>/migration.sql` folder per migration on the v1 RC, which dropped the journal to stop Git conflicts on it ([Upgrading to Drizzle v1](https://orm.drizzle.team/docs/upgrade-v1)). The v0 ledger is `__drizzle_migrations(id, hash, created_at)`, and `migrate()` reads only the newest `created_at` and applies journal entries with a later timestamp. That **high-water mark** silently skips an older-timestamped pending migration while printing "migrations applied successfully" ([drizzle-orm#5769](https://github.com/drizzle-team/drizzle-orm/issues/5769)). The stored hash is written and never compared ([drizzle-orm#6179](https://github.com/drizzle-team/drizzle-orm/issues/6179)), and the Expo migrator stores an empty string in it ([expo-sqlite migrator](https://github.com/drizzle-team/drizzle-orm/blob/main/drizzle-orm/src/expo-sqlite/migrator.ts)). v1 fixes the skipping by keying the ledger on migration name and applying every local migration whose name is absent ([migrator.utils.ts@rc5](https://github.com/drizzle-team/drizzle-orm/blob/rc5/drizzle-orm/src/migrator.utils.ts)). Both lines still run all pending migrations in one transaction, read the history **outside** that transaction, and take **no lock**, so two concurrent `migrate()` calls can each apply the same migration ([drizzle-orm#874](https://github.com/drizzle-team/drizzle-orm/issues/874)). The only fix in flight is a Postgres advisory lock ([PR #6451](https://github.com/drizzle-team/drizzle-orm/pull/6451)).

On Expo, migrations ride inside the JS bundle. `babel-plugin-inline-import` turns `.sql` files into strings, Metro adds `sql` to its source extensions, and a `useMigrations(db, migrations)` hook applies them at app start in one transaction ([Drizzle Expo docs](https://orm.drizzle.team/docs/connect-expo-sqlite)). Expo's own docs show a simpler ladder keyed on `PRAGMA user_version` ([Expo SQLite docs](https://docs.expo.dev/versions/latest/sdk/sqlite/)). On a phone, one process owns the file, so the missing lock never matters.

Turso's guide runs `drizzle-kit migrate` from CI against the remote URL, with runtime `migrate()` as the alternative ([Turso Drizzle guide](https://docs.turso.tech/sdk/ts/orm/drizzle)). Turso deprecated its server-side multi-database schemas and now tells per-tenant users: "You own the migration workflow, including version tracking, retries, and handling databases that are temporarily behind" ([Multi-tenancy at scale](https://turso.tech/blog/multi-tenancy-at-scale)).

Mature migrators add what Drizzle lacks. Prisma takes an advisory lock with a 10 s timeout, and it keeps a sticky failed state that blocks further deploys until someone resolves it ([Prisma docs](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/development-and-production), [Prisma patching](https://www.prisma.io/docs/orm/prisma-migrate/workflows/patching-and-hotfixing)). Rails raises `ConcurrentMigrationError` ([migration.rb](https://github.com/rails/rails/blob/main/activerecord/lib/active_record/migration.rb)). Expand–contract keeps two code versions working across a deploy ([Fowler, ParallelChange](https://martinfowler.com/bliki/ParallelChange.html)).

The lesson for bumbledb is that the lock exists only to make "read history, apply, record" one atomic step. A log entry created with `If-None-Match` is already that step.

## Every S3-native peer commits by creating the next key

| System | Commit point | Acknowledged after | Published write latency | Single-writer safety | Cold start |
|---|---|---|---|---|---|
| Graft v2 | `commits/{LSN}` created if absent | local commit; push is async | "high-latency writes at low cost" | create-if-absent only; divergence needs manual fix | commit metadata from LSN 1, pages lazy |
| Litestream 0.5 | none (LTX uploads unconditional) | local SQLite; shipped ~every 1 s | 1 s window | 30 s lease on `lock.json`, advisory | VFS reads LTX page indexes, pages lazy |
| SlateDB | `wal/{id}.sst` if absent; manifest CAS | memtable, or `await_durable` | Standard 50–100 ms; Express 5–10 ms | `writer_epoch` plus fencing WAL; GC boundary | read manifest, bump epoch, fence, replay WAL |
| Neon | safekeeper Paxos quorum | quorum ack; S3 async | not published | control-plane generations in keys | ~500 ms compute |
| Durable Objects / D1 | 3 of 5 cross-DC followers | follower quorum; R2 batched 10 s/16 MB | not published | old leader stopped on 3 of 5 | snapshot plus log |
| Delta Lake | `_delta_log/{v}.json` put-if-absent | file created | not published | optimistic concurrency | checkpoint plus log |
| Iceberg | catalog pointer swap | swap | not published | optimistic concurrency | metadata file |
| turbopuffer | CAS WAL object | object storage | p50 165 ms (500 kB) | CAS | cold query p50 874 ms |

Sources: [Graft remote.rs](https://github.com/orbitinghail/graft/blob/main/crates/graft/src/remote.rs), [Graft future work](https://graft.rs/docs/internals/future/), [Litestream VFS docs](https://litestream.io/how-it-works/vfs/), [leaser.go](https://github.com/benbjohnson/litestream/blob/main/s3/leaser.go), [SlateDB tuning](https://slatedb.io/docs/operations/tuning/), [SlateDB RFC 0001](https://github.com/slatedb/slatedb/blob/main/rfcs/0001-manifest.md), [Neon architecture](https://neon.com/docs/introduction/architecture-overview), [Neon cold starts](https://neon.tech/blog/cold-starts-just-got-hot), [SQLite in Durable Objects](https://blog.cloudflare.com/sqlite-in-durable-objects/), [Delta PROTOCOL.md](https://github.com/delta-io/delta/blob/master/PROTOCOL.md), [Iceberg spec](https://iceberg.apache.org/spec/), [turbopuffer architecture](https://turbopuffer.com/docs/architecture), [WarpStream low-latency docs](https://docs.warpstream.com/warpstream/kafka/advanced-agent-deployment-options/low-latency-clusters), [S2 intro](https://s2.dev/blog/intro).

**None of these systems commits through a mutable HEAD.** Graft has exactly two remote key types, `logs/{LogId}/commits/{LSN}` and `segments/{SegmentId}`. It writes the commit with OpenDAL's `if_not_exists` and finds the tip by issuing GETs until one returns NotFound ([Graft remote.rs](https://github.com/orbitinghail/graft/blob/main/crates/graft/src/remote.rs)). SlateDB numbers its manifests and treats the highest one as current. Its draft RFC 0032 lists a "CURRENT Pointer" among the rejected alternatives ([RFC 0032](https://github.com/slatedb/slatedb/blob/main/rfcs/0032-cached-probing-sequenced-metadata.md)). Delta commits by atomically creating the next-numbered `_delta_log/<v>.json`, which needs only put-if-absent ([Delta PROTOCOL.md](https://github.com/delta-io/delta/blob/master/PROTOCOL.md)). Before S3 had conditional writes, multi-writer Delta needed a DynamoDB LogStore ([delta.io, 2022](https://delta.io/blog/2022-05-18-multi-cluster-writes-to-delta-lake-storage-in-s3/)). Iceberg swaps a pointer through a catalog's check-and-put and handles a lost response as an explicit "unknown commit state" ([Iceberg configuration](https://iceberg.apache.org/docs/latest/configuration/)). bumbledb's proposal sits squarely in the Delta/Graft camp, and SlateDB's own designers have decided against the pointer bumbledb is removing.

**Fast acknowledgments come from moving the commit point, not from tuning S3 Standard.** turbopuffer pays for S3 Standard on every commit: it acknowledges only after a CAS-committed WAL file exists, caps a namespace at one WAL entry per second, and reports **p50 165 ms** ([turbopuffer architecture](https://turbopuffer.com/docs/architecture)). Cloudflare and Neon move the commit point to a quorum they run themselves. Cloudflare acknowledges once 3 of 5 cross-datacenter followers hold the WAL and uploads to R2 lazily in 10 s or 16 MB batches ([SQLite in Durable Objects](https://blog.cloudflare.com/sqlite-in-durable-objects/)), and Neon acknowledges on a safekeeper Paxos quorum ([Neon walservice](https://github.com/neondatabase/neon/blob/main/docs/walservice.md)). S2 and WarpStream move it to Express: S2 writes to a quorum of three Express buckets and WarpStream to a quorum of zonal Express buckets, for roughly **20–40 ms** acknowledgments with multi-AZ durability, while ordering comes from a sequencer or a single writer ([S2 intro](https://s2.dev/blog/intro), [WarpStream lazy log](https://www.warpstream.com/blog/the-art-of-being-lazy-log-lower-latency-and-higher-availability-with-delayed-sequencing)). Graft and Litestream defer durability instead, committing locally and shipping later, which leaves acknowledged writes on local disk until upload ([Graft consistency](https://graft.rs/docs/concepts/consistency/), [Litestream writable VFS guide](https://litestream.io/guides/vfs-write-mode/)). Turso's diskless redesign shows why that is unacceptable when the local disk belongs to an ephemeral function.

**Fencing is only as strong as the conditional write behind it.** SlateDB has the most rigorous design that uses S3 alone. A new writer bumps `writer_epoch` in a CAS'd manifest, then writes an empty "fencing WAL file" at the next WAL ID with `If-None-Match`, so a zombie's next WAL PUT collides and the zombie halts. SlateDB must fence both objects because "SlateDB does not/can not transactionally read-modify-write across the two" ([RFC 0030](https://github.com/slatedb/slatedb/blob/main/rfcs/0030-pluggable-wal.md)). Litestream's 30 s lease on `lock.json` uses `If-None-Match` and `If-Match`, but its LTX data uploads carry no conditional headers, which makes the lease coordination rather than a fencing token ([leaser.go](https://github.com/benbjohnson/litestream/blob/main/s3/leaser.go), [replica_client.go](https://github.com/benbjohnson/litestream/blob/main/s3/replica_client.go)). Graft uses neither epochs nor leases. On AlreadyExists it distinguishes "someone (including us) pushed the same commit" from "a DIFFERENT commit (divergence)" ([remote_commit.rs](https://github.com/orbitinghail/graft/blob/main/crates/graft/src/rt/action/remote_commit.rs)), and that distinction is exactly bumbledb's byte-compare rule.

**SlateDB also documents the hazard that every delete-capable, create-if-absent log must face.** A writer can stall mid-update, GC can then delete the ID it meant to create, and "create-if-absent can reuse that ID and report a stale update as successful." SlateDB closes the hole with a GC boundary object advanced by `If-Match`. Writers check the boundary after each create ([SlateDB GC](https://slatedb.io/docs/design/gc/), [RFC 0026](https://github.com/slatedb/slatedb/blob/main/rfcs/0026-garbage-collector-boundary.md)). Its cost analysis also condemns LIST-based discovery. An idle database polling with LIST issues 560 LISTs every five minutes, about **$24.19 per month**, and RFC 0032 replaces them with "GET N+1 until 404" probing to get under $5 ([RFC 0032](https://github.com/slatedb/slatedb/blob/main/rfcs/0032-cached-probing-sequenced-metadata.md)).

Finally, turbopuffer's object-storage queue walks the whole design path in one post. It starts with a single JSON file rewritten by CAS, adds group commit by buffering requests while a CAS write is in flight, then moves that loop into a stateless broker that serves every client, and makes broker failover safe because "CAS ensures correctness even with two brokers" ([turbopuffer queue](https://turbopuffer.com/blog/object-storage-queue)). bumbledb needs the first two steps now. The broker is an escape hatch if write contention ever becomes real.

## S3 Express buys 6 ms commits at the cost of one zone and unordered LISTs

### Conditional writes made S3 a coordination substrate in 2024–2025

S3 added conditional operations in four steps:

| Date | Feature |
|---|---|
| August 2024 | `If-None-Match: *` (create-if-absent) |
| November 2024 | `If-Match: <ETag>` (compare-and-swap) |
| September 2025 | Conditional DELETE |
| October 2025 | Conditional CopyObject |

All four are free and apply to both general purpose and directory buckets ([AWS, Aug 2024](https://aws.amazon.com/about-aws/whats-new/2024/08/amazon-s3-conditional-writes), [AWS, Nov 2024](https://aws.amazon.com/about-aws/whats-new/2024/11/amazon-s3-functionality-conditional-writes), [conditional deletes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-deletes.html), [AWS, Oct 2025](https://aws.amazon.com/about-aws/whats-new/2025/10/amazon-s3-conditional-write-functionality-copy-operations)).

The semantics matter for the submit loop. "The first write operation to finish succeeds" and later ones get **412**. A conflicting in-flight operation can instead return **409 ConditionalRequestConflict**, which is retryable for PutObject. For CompleteMultipartUpload, a 409 forces a whole new upload. In-progress multipart uploads are invisible to preconditions ([conditional writes guide](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html), [PutObject reference](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html)). Conditional requests must be SigV4-signed. S3 is strongly read-after-write consistent, single-key updates are atomic, and "There is no way to make atomic updates across keys" ([S3 consistency model](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel)).

One practitioner pitfall maps onto bumbledb directly. If a conditional PUT succeeds, its response is lost, and the SDK retries, the retry returns 412 against your *own* object. The fix is to embed a writer-unique ID and read the object back ([mohakchugh](https://mohakchugh.is-a.dev/blog/s3-conditional-writes-distributed-coordination)).

### Express is five times faster and adds append and rename

S3 Express One Zone stores data "on multiple devices within a single Availability Zone". AWS positions it for "single-digit millisecond PUT and GET latencies" ([S3 User Guide](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html)) and designs it for 99.95% availability. It adds three primitives that S3 Standard lacks. **Append** is a PutObject with `x-amz-write-offset-bytes` equal to the current size; a mismatch returns 400 `InvalidWriteOffset`, and each object is capped at 10,000 parts ([append guide](https://docs.aws.amazon.com/AmazonS3/latest/userguide/directory-buckets-objects-append.html)). **RenameObject** (June 2025) is atomic and supports destination `If-None-Match`, source preconditions, and an `x-amz-client-token` that makes retries truly idempotent ([RenameObject reference](https://docs.aws.amazon.com/AmazonS3/latest/API/API_RenameObject.html)). **Conditional DELETE** works on directory buckets too ([conditional deletes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-deletes.html)).

Three differences bite a commit protocol. On directory buckets "ListObjectsV2 does not return objects in lexicographical (alphabetical) order", there is no versioning and no event notification, and ETags are random strings rather than MD5 digests ([Differences for directory buckets](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-express-differences.html)). Separately, every zonal operation needs a `CreateSession` token that expires after five minutes. SDKs refresh it automatically ([CreateSession reference](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CreateSession)). Inside a VPC, Express traffic should use a gateway endpoint, because routing it through a NAT gateway caps throughput ([AWS re:Post](https://repost.aws/articles/ARwllpT3g9QH2zqh5Z5L2LgQ/s3-express-one-zone-throughput-capped-at-nat-gateway-bandwidth-use-a-vpc-gateway-endpoint)).

### Outside AWS, conditional-write support is uneven

R2 supports `If-None-Match` and `If-Match` on PutObject. The one portable primitive is **create-if-absent on a fresh key with a single PUT**. That is the only primitive bumbledb's commit path should depend on.

## The create-only log holds up; Express and five new representations finish it

### One Express PUT is the whole warm submit

Today a submit costs three serial round trips, with the LMDB write transaction held across two of them. At Turso's measured S3 Standard averages (19 ms GET, 31 ms PUT), three round trips add up to roughly **60–90 ms before any tail** (estimate).

The proposed loop has a better floor if one step is dropped on warm instances. A warm instance whose cache sits at tip `t` should decide against `t` and immediately PUT `log/{t+1}`. A pre-PUT catch-up GET is unnecessary because the create-only PUT already proves freshness. If the PUT succeeds, no entry existed after `t`, so the decision and the receipt check were both made against the true tip. If it fails with 412, the instance GETs `log/{t+1}`. If the entry is its own, the commit is done. Otherwise it applies the foreign entry, re-decides against `t+1`, and tries `t+2`.

The steady-state cost is therefore **one Express PUT: 6.4 ms average and 7 ms p99 in the same AZ, or 7 and 8 ms across AZs** ([Turso diskless](https://turso.tech/blog/turso-cloud-goes-diskless)). That matches Turso's PUT floor without Turso's 10–100 ms batching window. Each lost race adds one GET and one PUT, about 11 ms on Express (estimate). Strong reads that must observe the latest commit cost one `GET log/{tip+1}` returning 404, about 4 ms. Reads can avoid even that by carrying a bookmark. The submit returns its `seq`, and a later request waits until the local cache reaches that `seq`, which is how D1 sessions provide read-your-writes ([D1 read replication](https://blog.cloudflare.com/d1-read-replication-beta/)) and how sqld's `replication_index` works ([write_proxy.rs](https://github.com/tursodatabase/libsql/blob/main/libsql-server/src/connection/write_proxy.rs)).

Two representation changes make this loop sound. First, decide should run against an LMDB **read snapshot** and produce a ChangeSet value, which apply then writes in a short write transaction after the PUT succeeds, so no network round trip ever runs under LMDB's single write lock. Second, the writer state should be a sum type, `Idle{tip} | InFlight{tip, entry}`, which makes **two in-flight PUTs unrepresentable**. The log has no hash chain, so a writer that pipelined `t+2` on top of its own speculative `t+1` could see `t+2` land after another writer had won `t+1`. The entry would then sit on top of the wrong state, and nothing in the key space would reveal the mistake. Making the second PUT impossible to express removes that failure mode outright.

The Express-only primitives do not earn a place in v1. Append could hold up to 10,000 entries per segment object and turn tail catch-up into a single ranged GET ([append guide](https://docs.aws.amazon.com/AmazonS3/latest/userguide/directory-buckets-objects-append.html)), but AWS does not document the race between concurrent appenders, and append exists only on Express, so using it would fork the representation that FsStore and S3 Standard share. RenameObject's client token solves a retry ambiguity that byte comparison already solves, at the cost of an extra round trip. Conditional DELETE helps with leases and checkpoint cleanup, not with commits. The portable core, a single create-only PUT, is also the fastest path.

Express changes three other things. The first is **checkpoint discovery**: `ckpt/{inv(seq)}` with `LIST max-keys=1` returns an arbitrary key on a directory bucket. Checkpoints belong in a general purpose S3 Standard bucket, where LIST order is lexicographic, storage costs about a fifth of Express's price, and data is multi-AZ. That is Turso's exact split of WAL to Express and checkpoints to Standard ([AWS Storage Blog](https://aws.amazon.com/blogs/storage/how-turso-built-a-transactional-database-using-amazon-s3-express-one-zone/)). The second is **durability**. Express is single-AZ, so an AZ outage makes the log unavailable and an AZ loss would destroy entries written since the last Standard checkpoint; frequent checkpoints bound that window. S2's three-bucket quorum restores multi-AZ durability ([S2 intro](https://s2.dev/blog/intro)), but it gives up the single linearization point, and a majority-create protocol across buckets is no longer "dead simple", so it belongs in a later version. The third is **placement**: compute must sit in the bucket's region. bumbledb's native LMDB addon already requires a Node runtime with a filesystem, which points at Lambda-class compute in that region. If the compute runs outside AWS, single-region Tigris is the nearest option on vendor numbers, and R2 is cheapest but has no credible same-region latency data.

### Group commit needs no timer for one user

Every batching system in the evidence uses a timer: Turso 10–100 ms, SlateDB 100 ms, WarpStream 25–250 ms, turbopuffer 1 s, Litestream 1 s ([Turso durability](https://docs.turso.tech/cloud/durability), [SlateDB writes](https://slatedb.io/docs/design/writes/), [WarpStream docs](https://docs.warpstream.com/warpstream/kafka/advanced-agent-deployment-options/low-latency-clusters)). Each timer exists to amortize PUT cost across tenants, partitions, or namespaces. At Express prices, a million single-command commits cost $1.13, so a personal database has nothing to amortize.

The right policy is turbopuffer's queue rule: **buffer whatever arrives while a PUT is in flight, and flush it as the next entry the moment the PUT returns** ([turbopuffer queue](https://turbopuffer.com/blog/object-storage-queue)). An idle system adds zero latency. A busy one forms batches whose size tracks load. Throughput then scales with batch size rather than with PUT rate. One uncontended chain carries roughly 150 entries per second at 6.4 ms each (estimate), and every entry can hold many commands.

The `Commands` entry already is a batch. Each command needs its own outcome and receipt, decided in order against the state the earlier commands produced, so a rejected command never aborts its neighbors. A serverless instance that serves one request at a time rarely forms a batch. That is fine, because the policy degrades to one command per PUT. Cross-instance batching would need turbopuffer's broker, which is premature at personal scale.

### Acknowledge after the PUT; skip the output gate for now

Cloudflare's output gate lets code continue against local SQLite while holding every outgoing message until the writes it depends on are confirmed. On failure, the object restarts ([Durable Objects gates](https://blog.cloudflare.com/durable-objects-easy-fast-correct-choose-three/), [SQLite in Durable Objects](https://blog.cloudflare.com/sqlite-in-durable-objects/)). That works because a Durable Object is a fenced single writer, so its speculative outcomes almost never flip.

bumbledb is an optimistic multi-writer log. A 412 changes the predecessor state, so a speculative `Committed` can become `PreconditionFailed` after re-decision. Any response computed from the speculative state would then be wrong. The output gate would save at most one 7 ms PUT per request at the price of a re-execution path.

The rejected alternative, local durability with asynchronous shipping (Litestream, Graft), is worse still for serverless. The local disk dies with the instance, which is exactly the window Turso called "not really durable anywhere except the local disk" ([Turso diskless](https://turso.tech/blog/turso-cloud-goes-diskless)).

The v1 contract should therefore be Turso's, SlateDB's `await_durable` and S2's: **acknowledge only after the create-only PUT returns 200.** One consequence is a free win. The local LMDB is a disposable cache, so its commits need no fsync on the hot path. The log object is the durability point. The cache needs only crash detection, a recorded seq plus the content digest the cutover plan already proposes, so that a torn cache is rebuilt rather than trusted.

### The create-only slot is the fence, so epochs and leases add no safety

SlateDB needs `writer_epoch` and a fencing WAL for two reasons. Its writes can be acknowledged from the memtable before they are durable. And its commit state spans two objects, the manifest and the WAL, which cannot be updated atomically together ([RFC 0030](https://github.com/slatedb/slatedb/blob/main/rfcs/0030-pluggable-wal.md)). Litestream needs a lease because its data uploads are unconditional ([replica_client.go](https://github.com/benbjohnson/litestream/blob/main/s3/replica_client.go)).

bumbledb has neither property. It acknowledges only a won create, and its whole commit is one key. A zombie, such as a frozen serverless environment that thaws hours later with a PUT still in flight, can only target slot `t+1` of the state it last saw. That slot already exists, so the zombie gets 412, reads back a mismatch, and re-decides. That is Graft's create-if-absent-only safety argument ([Graft consistency](https://graft.rs/docs/concepts/consistency/)).

A lease would buy only liveness, by stopping several hot instances from repeatedly losing races to each other. The data for that is the turbopuffer broker, whose own failover is fenced by CAS ([turbopuffer queue](https://turbopuffer.com/blog/object-storage-queue)). It is not needed at personal write rates.

Byte comparison carries one obligation. **Every entry must embed a submission-unique nonce.** Suppose two clients submit byte-identical commands that decide to byte-identical entries at the same slot. Without a nonce, both would read back "ours", both would report success, and the effect would have happened once. Iceberg's unknown-commit-state handling and the 412-after-lost-response pitfall both point to the same rule: carry an ID inside the object and resolve ownership by reading it ([Iceberg configuration](https://iceberg.apache.org/docs/latest/configuration/), [mohakchugh](https://mohakchugh.is-a.dev/blog/s3-conditional-writes-distributed-coordination)). Treat 409, timeouts and 5xx as "ambiguous", and re-PUT the identical bytes. With that rule in place, hedging a slow PUT at about p99 (roughly 10–15 ms on Express, by inference) is also safe.

### Cold start: compacted image plus a bounded, parallel tail

Turso solved cold starts by never stopping its server, and solved large databases by fetching 128 KB segments lazily ([Turso 2025-05-20](https://turso.tech/blog/how-does-the-turso-cloud-keep-your-data-durable-and-safe)). Litestream's VFS and Graft also fetch pages lazily, through LTX page indexes or 64-page zstd frames ([Litestream VFS docs](https://litestream.io/how-it-works/vfs/), [Graft internals](https://graft.rs/docs/internals)). All three page through their own I/O layer. Turso had to rewrite SQLite as async to get partial sync ([sync benchmark](https://turso.tech/blog/sync-benchmark)).

LMDB reads through `mmap`, so lazy fetch would need a page-fault-driven fetch layer, which is exactly the kind of machinery the cutover plan's "dead simple" rule (D5) forbids. The serverless function also cannot be always-on. Full download of a compacted image is therefore the right v1 representation, and the work is to keep that download and the tail behind it small. Litestream's own guidance is that object-storage reads suit cold start but are "not fast enough for steady state" ([Litestream writable VFS](https://fly.io/blog/litestream-writable-vfs/)).

A cold open should issue Express `CreateSession` and `LIST ckpt/ max-keys=1` on the Standard bucket in parallel, then download the image with parallel ranged GETs. Because the checkpoint's key names its seq `c`, the instance can probe `log/{c+1…}` at the same time, in waves of about 32 parallel GETs until the first 404, and apply the tail as soon as the image is open. S3 Standard's per-request cost is about 30 ms plus about 20 ms per MiB, with 8–16 MiB the optimal request size ([GreptimeDB on Durner et al.](https://greptime.com/blogs/2024-01-31-paper-sharing)). On those numbers a 10 MB image arrives in about 80 ms over four streams, and a 256-entry tail takes eight waves of about 5 ms. The whole open should land around **100–200 ms** for a small database (estimate, unmeasured). For comparison, Neon's compute wakes in about 500 ms ([Neon](https://neon.tech/blog/cold-starts-just-got-hot)), turbopuffer's cold query p50 is 874 ms ([turbopuffer](https://turbopuffer.com/docs/architecture)), and Turso's embedded replicas took 718 ms to bootstrap 1 MB over the internet ([sync benchmark](https://turso.tech/blog/sync-benchmark)).

The current hydration re-judges the whole database. That step should go, because the checkpoint is written by trusted code and can be verified against its content digest.

The tail must be bounded by policy, because the current default of an unbounded tail with no automatic checkpoint is what makes cold opens replay all of history. Cloudflare snapshots when the logs since the last snapshot exceed the database size, which bounds recovery to about twice the database size ([SQLite in Durable Objects](https://blog.cloudflare.com/sqlite-in-durable-objects/)). Turso checkpoints about every 1 MB ([Turso 2025-05-20](https://turso.tech/blog/how-does-the-turso-cloud-keep-your-data-durable-and-safe)). bumbledb should checkpoint when either the entries since the last checkpoint pass N (a few hundred, chosen so the tail probe stays under about 50 ms) or the log bytes since the last checkpoint pass the image size. Any instance that replays more than N entries during a cold open should write a checkpoint itself, so a long tail is paid for once.

If images grow large enough that frequent full uploads hurt, one coarser derived object fixes it without changing the commit protocol. It is a Litestream-style packed range `pack/{start}` holding K aligned entries ([Litestream v0.5](https://fly.io/blog/litestream-v050-is-here/)).

### Ship decided row effects, not LMDB pages

Turso's history is the decisive evidence. Physical page shipping cost 4 KB per tiny write, made unrelated writes conflict, and diverged across checkpoints until replicas needed re-bootstrapping ([sync benchmark](https://turso.tech/blog/sync-benchmark)). LMDB makes this worse. Every write copies the root-to-leaf path on write, and page numbers are local accidents of allocation history, so a compacted copy renumbers everything.

Turso's current designs split cleanly by layer:

| Layer | Turso's representation | Source |
|---|---|---|
| Increments | logical; the MVCC log records changed rows | [Turso group commit post](https://turso.tech/blog/turso-group-commit) |
| Snapshots | physical; pages are pulled so replicas end byte-identical | [Turso Sync launch](https://turso.tech/blog/introducing-databases-anywhere-with-turso-sync) |

bumbledb's proposal already has that shape, with logical entries and physical images. One refinement matters. The current design "replays foreign decisions with full re-judgment", which makes catch-up cost a full decide per entry and ties past outcomes to the current engine version. An entry should instead carry the command IDs, the per-command outcomes, and the **decided ChangeSet**, so that apply is a deterministic row-level write that never re-judges. The same representation makes receipts cheap. Turso bounds its idempotency table at one row per client ([database_sync_operations.rs](https://github.com/tursodatabase/turso/blob/main/sync/engine/src/database_sync_operations.rs)). A `client_id → last seq` map would keep bumbledb's receipt index from growing with every command.

### Checkpoints are disposable; log keys must never disappear

Checkpoints and log entries carry opposite deletion risks. A checkpoint is a pure function of the log, so a stale process that re-creates an old `ckpt/` key writes a correct image of an old state. Readers pick the newest image anyway, so the stale copy is harmless. Checkpoints can therefore be garbage-collected by keeping the newest few and applying a minimum age, so an in-progress cold-open download does not 404. They should still be written create-only, or named with their digest. Compaction output need not be byte-deterministic, and ranged GETs across two overwritten versions would stitch two different images together.

Log keys are the opposite. If GC deletes `log/{s}` after folding it into a checkpoint, a stale writer that decided at `s−1` re-creates `log/{s}`, gets 200, and reports success for a commit that no reader starting from the checkpoint will ever see. That is SlateDB's documented hole ([SlateDB GC](https://slatedb.io/docs/design/gc/)). Time-based fixes are weak in serverless, where a frozen environment can thaw long after any `min_age`. SlateDB's boundary object works, but it adds a read to the commit path.

The representation-first fix is to **never let a log key disappear**. In v1 that means never deleting, which is exactly what the proposal does, and at personal scale it costs cents: three hundred thousand 2 KB entries a month add about $0.07 a month of Express storage. When GC becomes necessary, it should overwrite rather than delete, replacing a folded entry with a tiny `Compacted{ckpt}` stub. The key still exists, so the stale writer's `If-None-Match` still fails with 412, and its read-back shows a stub that tells it to re-hydrate from the named checkpoint. For the same reason, `log/` must never carry a lifecycle expiration rule, which would silently reopen the hole.

### Poll with GET, never LIST, and the bill rounds to cents

The proposal already finds the tip with `GET log/{tip+1}`, which is Graft's practice and SlateDB's planned fix ([RFC 0032](https://github.com/slatedb/slatedb/blob/main/rfcs/0032-cached-probing-sequenced-metadata.md)). LIST belongs only in a cold open, and only against the Standard checkpoint bucket.

At 10,000 commits a day, with 2 KB entries, a 50 MB image checkpointed every 1,000 entries, a million freshness probes, and 3,000 cold opens a month, the arithmetic from list prices is:

| Monthly line item | Log on Express, checkpoints on Standard | Everything on S3 Standard |
|---|---|---|
| 300k commit PUTs | $0.34 | $1.50 |
| 1M tip probes (GET returning 404) | $0.03 | $0.40 |
| Log storage added per month of history | $0.07 | $0.01 |
| Checkpoints: 300 PUTs, 3 retained, 3,000 LISTs plus ranged GETs | ~$0.03 | ~$0.03 |
| One poller using LIST every second instead (avoid) | n/a on Express | $12.96 |

Request cost is not a design driver at this scale. Latency is, and so is never polling with LIST.

### Migrations become one atomic log entry, with a deadline on Freeze

The proposal's core insight is right, and it is strictly better than Drizzle. A `Migration` entry created at `tip+1` makes "read the applied list, decide what to run, record it" a single atomic act. Drizzle reads history outside its transaction and takes no lock ([drizzle-orm#874](https://github.com/drizzle-team/drizzle-orm/issues/874)), and Prisma, Rails and Ecto need advisory locks to get the same guarantee. When several new-code instances cold-start at once, one wins the slot, and the others get 412, apply the winner's entry, recompare, and proceed with no special case.

Four refinements close the remaining gaps. The first makes the comparison a **four-way type**: the bundled list and the applied list compare as a prefix relation whose outcomes are Equal, Behind (run migrations), Ahead (`SchemaAdvanced`) and Diverged (error). The ledger should be keyed by name plus content hash, the hash should actually be verified, which Drizzle never does ([drizzle-orm#6179](https://github.com/drizzle-team/drizzle-orm/issues/6179)), and no timestamp high-water mark should decide anything ([drizzle-orm#5769](https://github.com/drizzle-team/drizzle-orm/issues/5769)).

The second gives **Freeze a deadline written into the entry**. Freeze exists for migrations that run longer than the gap between commits. Without a deadline, a crashed migrator or a rollback to old code leaves the database frozen with no one entitled to thaw it. With the deadline as data, any process may append Thaw once it passes, and `If-None-Match` arbitrates a race between a late Migration and a Thaw, so the lease is just data inside an entry.

The third makes **failure sticky**, as Prisma does ([Prisma patching](https://www.prisma.io/docs/orm/prisma-migrate/workflows/patching-and-hotfixing)). `Thaw` should carry `MigrationRejected{name, hash, violations}`, and new code bundling the same hash should fail `open()` loudly instead of cycling Freeze and Thaw on every cold start. The fourth makes the **Migration entry carry its result**, a reference to a post-migration image or a ChangeSet, so other replicas apply it without running migration code they may not have.

During a rolling deploy, old code gets `SchemaAdvanced` on writes. The overlap window should therefore be short: run `bumbledb migrate` as a deploy step before traffic shifts, as Prisma recommends ([Prisma docs](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/development-and-production)). Startup migration stays as the fallback for local and development use. When old and new code must truly coexist, expand–contract migrations are the discipline ([Fowler](https://martinfowler.com/bliki/ParallelChange.html)).

### Placement: a sans-IO Rust core driven by TypeScript

Moving object I/O into TypeScript is sound. The app's own S3 client already handles SigV4 signing and Express session refresh ([CreateSession reference](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CreateSession)), Effect makes timeouts, retries and hedges declarative, and the SDK's automatic retries are harmless because the own-write 412s they can cause are exactly what byte comparison resolves. The boundary should follow Turso's engine pattern ([async-io-model.md](https://github.com/tursodatabase/turso/blob/main/docs/agent-guides/async-io-model.md)). The Rust core is a sans-IO state machine. It emits object-store requests as data, such as `Create{key, bytes}`, `Get{key}` and `List{prefix}`, and consumes their results. It owns every invariant: the nonce, one in-flight PUT, the ownership decision, and checkpoint cadence. TypeScript only executes the requests. That keeps the protocol testable by deterministic simulation in Rust, which is the practice Turso credits for its server rewrite ([Turso durability docs](https://docs.turso.tech/cloud/durability)).

The `ObjectStore` interface then needs four verbs: GET, create-if-absent PUT, plain overwrite PUT (for future stubs), and LIST, used only for checkpoint discovery and tooling. DELETE is confined to checkpoints.

## Conclusion

The research changes the question. "How do we make S3 fast?" turns out to be the wrong framing. **Where does the commit point live, and how many round trips stand in front of it?** Turso's speed comes from a 6.4 ms Express PUT behind which nothing else waits, plus a cache that never needs to be durable. bumbledb's create-only log reaches the same floor with one PUT and no server.

It also beats Turso's added latency at personal scale, because there are no tenants to batch across and so no window. Optimism scales down well: the costs of an optimistic multi-writer design (contention, cold starts, single-AZ exposure) grow with write rate and database size, and at personal scale both are small. The proposal's remaining weaknesses are almost all places where a representation is missing: a nonce, a ChangeSet in the entry, a writer state that cannot hold two in-flight PUTs, a deadline inside Freeze, and a stub in place of a delete. Each one deletes a failure mode rather than handling it, which is the owner's principle, and that is a good sign the design is close to finished.

### Prioritized recommendations

| Priority | Recommendation | Why |
|---|---|---|
| P0 | Embed a submission-unique nonce in every entry. Resolve 412, 409, timeouts and 5xx by read-back comparison, and re-PUT identical bytes when ambiguous. | Without it, identical commands from two clients both read back "ours". It also makes hedged PUTs safe. |
| P0 | Make the writer state `Idle{tip} \| InFlight{tip, entry}`, so a writer can never have two log PUTs in flight. | With no hash chain, a pipelined `t+2` could land on another writer's `t+1`. |
| P0 | Never delete `log/` keys or put a lifecycle rule on them. Fold old entries later by overwriting with a `Compacted{ckpt}` stub. | Closes the stale-writer re-create hole that SlateDB documents. |
| P0 | Entries carry command IDs, outcomes and the decided ChangeSet. Apply never re-judges. | Cheap, deterministic catch-up; avoids Turso's page-shipping failures. |
| P1 | Put `log/` on an S3 Express directory bucket and `ckpt/` on an S3 Standard bucket in the compute's region. Use LIST only on Standard. | About 7 ms commits, a working `LIST max-keys=1`, and multi-AZ checkpoints. |
| P1 | Warm submit is decide then PUT, with no pre-PUT GET. Decide on a read snapshot and apply in a short write transaction. Do not fsync the cache. | Brings a submit from 3 round trips plus an fsync down to 1 round trip, with no network I/O under the LMDB lock. |
| P1 | Group commit: queue commands while a PUT is in flight and flush when it returns, with no timer. | Zero added latency when idle; throughput tracks load. |
| P1 | Checkpoint automatically after N entries, or when log bytes reach the image size. Any cold opener that replays more than N entries writes a checkpoint. Verify images by content digest, not re-judgment. | Bounds cold-start replay. |
| P1 | Cold open runs CreateSession, LIST, ranged image GETs and 32-wide tail waves in parallel. | Estimated 100–200 ms for small databases. |
| P1 | Return the commit `seq` as a bookmark. Strong reads cost one `GET tip+1`. | Read-your-writes without per-read probes. |
| P2 | Migration ledger keyed by name plus verified hash, with a four-way comparison. The optimistic Migration entry is the default, Freeze carries a deadline, and rejection is sticky. | Atomic, lock-free, cannot wedge, fails loudly. |
| P2 | Run `bumbledb migrate` as a deploy step. Keep startup migration for local and development use. | Keeps the window in which old code gets `SchemaAdvanced` short. |
| P3 | Make the Rust core sans-IO, emitting requests as data, and let TypeScript with Effect and the app's S3 client execute them. | Deterministic simulation tests; the SDK handles Express sessions. |
| P3 | Test lanes: a mutex-wrapped s3s server, real S3 Standard, and a real Express lane with a racing-create contract probe. | Directory buckets differ in LIST order, ETags and session auth; local emulators are racy or archived. |
| Defer | Express append segments, RenameObject, a 3-bucket Express quorum, a write broker, lazy page fetch. | Each adds a second representation or a service before evidence demands it. |

### Open risks

| Risk | Consequence | Mitigation or status |
|---|---|---|
| Express PUT latency rests on one 1,000-op microbenchmark; no independent p99.9 exists for conditional PUTs | The 7 ms target may have a fatter tail | Measure in the Express CI lane; hedge at about p99 |
| Express is single-AZ | An AZ outage halts writes; an AZ loss destroys entries since the last checkpoint | Frequent Standard checkpoints; a quorum or a Standard mirror later |
| Contention among many hot serverless instances | Repeated 412 losses, starvation for individual writers | Fine at personal rates; turbopuffer-style broker if needed |
| Cold start grows with image size (no lazy fetch in LMDB) | Large databases open slowly | Compact images, ranged GETs, packs; revisit if images pass ~100 MB |
| LMDB image portability between the macOS dev machine and Linux functions is unproven | A checkpoint taken on one platform may not open on the other | The cutover plan already lists this test; fall back to a logical row dump if it fails |
| Provider differences in 412 vs 409, and unknown billing of failed conditional requests | Misclassified outcomes or cost surprises | Treat all non-200 results as "re-read"; keep Garage and B2 out of scope |
| Freeze deadlines rely on wall clocks | Clock skew could thaw early or late | Generous deadlines; a Thaw can only land at a slot decided against the true tip |
| Express sessions expire every 5 minutes; Express ETags are random | An extra round trip on cold start; ETag cannot verify content | Overlap CreateSession with LIST; compare bodies, not ETags |
| Lambda-in-VPC traffic to Express through NAT is bandwidth-capped | Slow image downloads | Use a VPC gateway endpoint |
| The log grows forever in Express storage | Slowly rising cost | Stub-overwrite GC when needed; never use lifecycle deletes |
| Turso's reference designs may shift after the Supabase acquisition | Less public detail to borrow from | No dependency; the evidence used here is already published |
