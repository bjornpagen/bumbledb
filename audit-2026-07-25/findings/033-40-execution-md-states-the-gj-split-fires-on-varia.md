## 40-execution.md's GJ-split condition says "different earlier nodes" — the split also fires (and must) when a variable first binds at the probe's own node

incoherence | low | CONFIRMED | gj-split-live
outcome: fixed 6914471b

### Summary
The architecture doc states the GJ split fires on "a probe subatom carrying two or more variables first bound at different **earlier** nodes" (docs/architecture/40-execution.md:727-731). The implementation's condition is strictly wider: `gj_split` splits whenever the vars' first-bound nodes differ at all (crates/bumbledb/src/plan/fj/gj_split.rs:33), including the case where one variable is first bound by the probe's own node's opening subatom — which is not an edge case but the canonical triangle shape the split exists to lower.

### Evidence
- **Doc condition** — docs/architecture/40-execution.md:727-731: "then the **GJ split** (ruled 2026-07-23, R19): a probe subatom carrying two or more variables first bound at different earlier nodes splits into per-variable lookup subatoms, each placed at the node where its variable is first bound".
- **Code condition** — crates/bumbledb/src/plan/fj/gj_split.rs:33: `if vars.iter().all(|v| first_bound[v] == first_bound[&vars[0]])` → skip; otherwise split. Only "different nodes", never "earlier". The module doc (gj_split.rs:5-9) says "first bound at different nodes", and the placement comment (gj_split.rs:19-20) states the invariant "a variable's lookup lands exactly at its binding node, never earlier" — i.e., same-node landing is expected.
- **Why same-node binding is routine** — crates/bumbledb/src/plan/fj/binary2fj.rs:38-61: occurrence k+1's probe subatom is pushed onto the node opened by occurrence k, whose opening subatom carries occurrence k's `remaining` (newly bound) vars. Any closing atom sharing a variable with the immediately preceding occurrence's fresh vars therefore carries a var first bound at the probe's own node.
- **The repo's own canonical test exhibits exactly this** — crates/bumbledb/src/plan/fj/tests/build.rs:45-102 (`gj_split_lowers_the_triangle_to_the_gj_plan`): for `Q :- R(x,y), S(y,z), T(z,x)` with order [R,S,T], the pre-split plan is asserted as node0 = `[R{X,Y}, S{Y}]`, node1 = `[S{Z}, T{Z,X}]`. T's probe carries Z, first bound at node1 itself (by S's opening subatom), and X, first bound at node0. The test then asserts `gj_split` splits it — the step the doc itself credits with giving a production node its second cover. Under a strict reading of "different earlier nodes", Z is not bound at an *earlier* node, so this probe would not qualify.

### Failure scenario / impact
Documentation-only; no runtime defect. But under the repo's verify-against-in-repo-papers rule, an auditor checking the planner against 40-execution.md would conclude that triangle-shaped plans like `A(x), B(x,y), C(y,x)` legitimately keep a monolithic two-word closing probe (the binary-join shape R19 exists to erase), misclassifying the working GJ-end lowering as absent — or, worse, signing off a future regression that stops splitting the canonical cyclic case as doc-conformant.

### Suggested fix
In docs/architecture/40-execution.md:728-729, drop "earlier": "…a probe subatom carrying two or more variables first bound at different nodes splits into per-variable lookup subatoms, each placed at the node where its variable is first bound (which may be the probe's own node — the closing atom of a cycle shares a variable with the node's opening subatom)." This matches gj_split.rs's stated placement invariant ("lands exactly at its binding node, never earlier") and the triangle test.
