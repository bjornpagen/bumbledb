## Naive twin's capacity witness tie-break order diverges from the engine's for permuted or str-typed parent keys

category: bug | severity: medium | verdict: CONFIRMED | finder: lean-capacity-drift
outcome: fixed 808406eb

### Summary

When one capacity statement is violated at several parents in a single delta, the differential's two sides disagree on WHICH parent's measure is witnessed. The naive model reports the violator with the least projected key tuple in the CAPACITY statement's `target.projection` written order under decoded-`Value` comparison; the engine reports the first-discovered violator, and its discovery order is ascending DeterminantImage BYTE order in the DECLARED KEY statement's projection order. The two orders coincide only for order-preserving encodings in aligned field order — they diverge for (a) a target projection that permutes the declared key (explicitly licensed by set-equality key resolution) and (b) str-typed key fields (determinant bytes are intern ids in first-intern order, not lexicographic). Since the differential compares `Violation::Capacity` including the u128 measure strictly, a legal schema+delta produces a spurious `Divergence::Write`.

### Evidence (verified)

- **Naive tie-break** — `crates/bumbledb-bench/src/naive.rs:507-522`: on violation, builds `key: Vec<Value>` by mapping `target.projection` (written order) over the parent and keeps the witness whose `Tuple(key)` is least. `Tuple`'s order is decoded-value order (`crates/bumbledb-bench/src/naive/tuple.rs:16-67`); `Value::String` compares **raw UTF-8 bytes** (`tuple.rs:55-56`). The doc comment at `naive.rs:474-480` asserts the twins "agree on WHICH parent's total is reported" with no caveat for permuted projections or intern-id keys.
- **Engine discovery order** — `crates/bumbledb/src/storage/commit/plan.rs:236` (`BTreeMap<CapacityId, BTreeSet<DeterminantImage>>`), flattened in ascending image byte order at `plan.rs:276-282`. Both touched halves are in DECLARED-KEY determinant order: the source (child) half via `capacity_child_image` → `keys::permuted_determinant_image` with the validation-minted `key_permutation` (`crates/bumbledb/src/storage/commit/judgment.rs:742-768`), the target half via `key_statement.projection` directly (`plan.rs:462-473`). `check_capacities` judges in plan order (`judgment.rs:715-735`).
- **First-discovered witness survives** — `crates/bumbledb/src/error.rs:1141-1151`: `Violations::seal` stable-sorts by `citation()` = `(StatementId, Option<Direction>)` (`error.rs:1073-1084`; capacity direction is `None`) then `dedup_by_key`, so per statement the first violation in walk order — the least declared-key byte image — is the one reported.
- **Permuted projections are legal** — `crates/bumbledb/src/schema/validate.rs:1381-1397`: target-key resolution matches by `FieldSet` **set equality** (the canonical projection identity sorts, `validate.rs:333`); the inverse permutation is minted at `validate.rs:1418-1428` precisely to re-order permuted projections into determinant order. The naive model consumes the raw `StatementDescriptor` and never sees this canonicalization.
- **str determinant bytes are intern ids** — `crates/bumbledb/src/encoding.rs:107-118`: `ValueRef::String(u64)` "carries an intern id"; ids are minted in first-intern order, so byte order ≠ lexicographic order. str columns are refused only on **closed** relations (`validate.rs:1634-1642`), so str-keyed ordinary parents are legal. (I64 is sign-flipped big-endian, `encoding/encode.rs:18-22`, hence order-preserving — the divergence is confined to the two claimed cases.)
- **Strict comparison** — `crates/bumbledb-bench/src/differential.rs:132` compares `Verdict`s by equality; `cited()` carries the `measure` into the compared value (`differential.rs:207-212`).
- **Silent today** — `random_descriptor`'s only consumers are theorygen's own `#[test]`s (`crates/bumbledb-bench/src/corpus_gen/theorygen.rs`); the Ledger bench schema declares no capacity statement (`crates/bumbledb-bench/src/schema.rs:15-79`); the hand differential capacity tests use single-u64-field, order-aligned keys only (`crates/bumbledb-bench/src/differential/tests/marks.rs:23-121`).

### Failure scenario / impact

Schema: key `ROOM(x, y) -> ROOM`; capacity `ROOM(y, x) <={0..0} BOOKING(u, v)` (legal: set-equal projection resolves to the key with a minted permutation). Committed parents P1=(x=1, y=9) and P2=(x=2, y=0); one delta inserts one BOOKING child under P1 and two under P2. Engine: touched parents walk in (x,y) declared-key byte order → P1 first → sealed witness measure = 1. Naive: least (y,x) `Value` tuple → P2 (y=0) → measure = 2. Both sides say `Aborted` citing the same statement, but measures 1 vs 2 → `Divergence::Write` on a legal input. The str analogue needs no permutation: two str-keyed parents whose intern order (insert order) inverts lexicographic order. Impact: any future randomized or hand-written differential lane over capacity theories with permuted or str-keyed parents reports a false divergence; the naive.rs:474-480 alignment comment documents a law the code does not have.

### Suggested fix

Make the witness identity representational on both sides: define the surviving capacity witness as the violator least in DECLARED-KEY determinant order (the engine's existing deterministic order), and have the naive derive its tie-break key through the same canonical field order — key-projection order, intern-id-aware (the naive would need to model the dictionary's mint order, which it already observes via insert order). Alternatively — simpler and arguably more honest about what the differential can promise — widen the capacity comparison to statement identity, comparing the measure only when the cited parent facts agree (the engine's `CitedFact` values are available for exactly this). Either way, land with a marks test using a two-field permuted key and a str-keyed parent, and fix the naive.rs:474-480 comment to state the actual tie-break law.
