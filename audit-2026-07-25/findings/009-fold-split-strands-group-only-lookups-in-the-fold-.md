## fold_split strands group-only lookups in the fold-domain node: per-fold-element probing, forfeited second cover, and (last-node shape) a defeated scan-fold pushdown

perf | medium | CONFIRMED | gj-split-live
outcome: fixed 3e7b8920

### Summary
`fold_split` splits a mixed opening subatom into a group-prefix node and a fold-domain suffix node but leaves ALL of the node's sibling lookup subatoms in the suffix. A lookup whose variables are entirely group variables ends up one node AFTER its binding node: it is probed once per surviving (group x fold-domain) batch element instead of once per group, groups with no lookup match enumerate their whole fold domain before dying, the prefix node's free second cover (R19's dynamic-choice payoff) is forfeited, and — in the fully-factored shape where the fold-suffix node is the plan's last node — the stranded lookup makes the scan-fold pushdown that `fold_split` exists to enable decline entirely.

### Evidence (all verified against the working tree)
- `crates/bumbledb/src/plan/fj/fold_split.rs:32-47` — `let node = plan.nodes.remove(i); let mut suffix = node.subatoms;` then only `suffix[0]` is replaced with `{occ, fold_vars}`; `subatoms[1..]` stay in the suffix node verbatim. The freshly inserted prefix node (lines 39-47) carries only the group-vars opening subatom.
- `crates/bumbledb/src/api/prepared/build.rs:859-861` — `fold_split` runs first, `gj_split` immediately after.
- `crates/bumbledb/src/plan/fj/gj_split.rs:33-36` — `if vars.iter().all(|v| first_bound[v] == first_bound[&vars[0]]) { s += 1; continue; }`: any subatom whose variables share one first-bound node is skipped, so only multi-binding-node probes get re-placed. After `fold_split`, group vars are first bound at the prefix node, so the group-only lookup sitting at the suffix node is exactly this skipped case — contradicting the invariant `gj_split.rs:19-20` states ("a variable's lookup lands exactly at its binding node, never earlier"): here it lands later.
- `crates/bumbledb/src/exec/run/probe_pass.rs:202-239` and the line-parallel twin `crates/bumbledb/src/exec/run/run_node.rs:396-439` — every non-cover subatom is gathered/hashed/probed once per surviving batch element. At the suffix node that is |surviving group x fold| probes; at the prefix node it would be |distinct groups| (prefix entries <= suffix elements, since every surviving group contributes >= 1 fold element).
- `crates/bumbledb/src/exec/run/pump.rs:129-178` — each node's cover is drawn per pending entry, so a group failing the lookup at the prefix would die BEFORE its fold domain is ever enumerated; today it dies per-element at the suffix.
- `crates/bumbledb/src/plan/fj/derive_nodes.rs:38-46` — covers are subatoms whose vars equal the node's `new_vars` exactly; a group-only lookup moved to the prefix (whose `new_vars` are the group vars) mints the second cover, enabling the dynamic group-key intersection R19 introduced dynamic cover choice for.
- **Aggravating, found during verification:** `crates/bumbledb/src/exec/run/leaf_precompute.rs:24` gates the leaf fast path on `plan.nodes()[last].subatoms.len() == 1`, and `crates/bumbledb/src/exec/run/scan_table.rs:57` (`sink.begin_scan`) is only reachable through that path. When the sibling atom factors fully into the mixed node (e.g. a unary dimension atom `Promo(g)`), the fold-suffix node IS the last node, and the stranded lookup makes the entire scan-fold pushdown decline — the split's stated purpose (`fold_split.rs:5-17`) is defeated for exactly the dimension-bound OLAP shape it serves.
- No pin blesses this: the only `fold_split` tests (`crates/bumbledb/src/plan/fj/tests/build.rs:148-206`) exercise single-subatom nodes; the mixed-node-with-sibling-lookup shape is untested.

### Failure scenario / impact
Any aggregate-head rule whose grouped atom shares its group variables with a sibling lookup atom — `Q(g, count(f)) :- Sales(g, f), Promo(g, ...)`. With a 500k-row fact table and 1k groups, the dimension probe runs ~500k times instead of ~1k (a fold-fanout multiple on probe count), groups with no dimension match still enumerate their full fold domain before dying, and in the fully-factored unary-sibling shape the scan-fold pushdown never fires at all. Correctness is unaffected.

### Suggested fix
In `fold_split`, partition the node's remaining subatoms by intersection with `fold_vars`: lookups touching no fold variable move into the prefix node (their variables are all bound by the prefix or earlier; placement there is provably never worse since prefix entries <= suffix elements, and it restores the last-node single-subatom shape the scan pushdown requires), the rest stay in the suffix. The broader alternative — generalizing `gj_split`'s placement rule to relocate ANY lookup to its single latest first-bound node — unifies the repair and mints the second cover, but the `fold_split`-local partition is the provably-never-worse scope. Land with a composed fold_split→gj_split unit test (mixed node with a group-only sibling lookup) and an aggregate-over-filtered-group e2e probe-count pin via the introspection counters.
