## Scenario cold-trace path leaks a live capture on prepare/execute error

bug | low | CONFIRMED | obs-estate
outcome: fixed ea3d6792

**Summary.** `capture_query` in `crates/bumbledb-bench/src/scenarios/trace.rs` hand-rolls the capture pairing for its cold half: `obs::start_capture()` followed by fallible calls with `?` before the `obs::finish_capture()` drain. On a prepare/execute error the function returns with the thread-local trace buffer still live. Since captures are idempotent-extend (a later `start_capture` inherits, never resets, a live buffer), the next capture on the thread would contain the failed query's events. Latent today — the error propagates and kills the run — but it violates the drain contract the shared harness helpers keep.

**Evidence (verified).**
- `crates/bumbledb-bench/src/scenarios/trace.rs:57-71` (Query branch): `obs::start_capture()` (57) → `cold_span` (58) → `db.prepare(&q).map_err(...)?` (59-61) → cold execute `...?` (63-64) → `emit(..., obs::finish_capture(), ...)` (66-71). The `?` at 61 and 64 return before the drain at 69. Same shape in the KeyedGet branch: start at 92, `?` at 94-95, drain at 100.
- `crates/bumbledb-bench/src/harness/traced.rs:9` and `:29` state the contract — "The closure's error (the capture is drained either way)" — and both `traced_sample` (finish at line 19, `?` at 21) and `traced_cold_sample` (finish at 46, `?` at 47) honor it. `trace.rs`'s cold half is the only capture site in the bench crate whose drain is unreachable on error (checked all `start_capture` call sites: tripwires.rs, sweep.rs, displaced/tests.rs pair infallibly).
- `crates/bumbledb/src/obs.rs:483-492`: `start_capture` is `get_or_insert_with` — "a nested (or unwound-over) start extends the live capture, never destroys it". Only `finish_capture` (494-504) takes the buffer. So a leaked capture survives into the next query's capture.
- `crates/bumbledb/src/obs.rs:542-556`: `SpanGuard::drop` records if the buffer is live — on the early return the `cold_span` SAMPLE event (plus any engine spans prepare emitted before failing) lands in the leaked buffer.
- Latency: `crates/bumbledb-bench/src/scenarios/run_query.rs:348-350` `?`-propagates `capture_query`'s error, and `scenarios/run.rs:34` (`reports.push(run_query(...)?)`) propagates out of the scenario loop — today the process dies and no contaminated artifact is written.

**Failure scenario / impact.** Any future per-query error tolerance in the scenario driver (the DNF-tolerant pattern other lanes use), or a test harness running two captures on one thread across a failure: query A's prepare fails mid-capture; query B's cold capture inherits A's SAMPLE span and partial engine spans; B's `.json`/`.folded` artifacts charge A's prepare time to B's stacks with no error surfaced anywhere. (Minor correction to the finding: the tick anchor is a process-global `OnceLock` — obs.rs:452-455 — so the mixed events share one coherent timeline; the corruption is foreign events in B's fold, not a skewed clock.)

**Suggested fix.** Mirror `traced_sample`'s shape: run the fallible cold body in a closure, call `finish_capture()` unconditionally, then `?`-propagate (emit the events on success, drop them on error). Cleaner: lift the cold half into a `traced_cold` variant beside `traced_sample`/`traced_cold_sample` in `harness/traced.rs` so no lane hand-rolls the start/finish pairing — the contract lives in one place, and this becomes unrepresentable.
