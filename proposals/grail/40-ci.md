# 40 — The CI lane

Amazon Linux is law: the linux artifacts are built and tested inside an
`amazonlinux:2023` arm64 CONTAINER, because glibc linking is decided by
the build userspace and AL2023 (glibc 2.34) is Lambda's runtime floor —
an Ubuntu-24.04 userspace (glibc 2.39) can mint a `.node` that does not
load where it deploys. The GitHub-hosted arm64 runner is only the host
kernel under the container; no build or test step executes in the
host's Ubuntu userspace.

One new workflow, `bumbledb-log.yml`, on the c-abi precedent (path
filters over crates/bumbledb-log/**, ts-log/**, ts/**, the workflow
itself):

- **Job linux-arm64** — runs-on the arm64 runner, `container:
  amazonlinux:2023`. Inside: dnf toolchain (gcc, nodejs22, git),
  rustup via rust-toolchain.toml; build the napi `.node` and the
  `bumbledb-log-duty` binary; run the battery against the freshly
  built artifacts — cargo fmt/clippy `-D warnings`/test for
  crates/bumbledb-log, the ts/ suite, the ts-log suite (direct-command
  spellings; frozen lockfiles) — so what is tested IS what deploys;
  upload `bumbledb.linux-arm64.node` and `bumbledb-log-duty` as run
  artifacts.
- **Job darwin** — macos-latest, the same battery on the reference
  host, no artifacts (the owner's machine publishes darwin).

The credential-gated S3 smoke (30) runs in either job iff the repo
secrets exist, loud-skips otherwise. The existing ci.yml lanes are
untouched — this workflow owns the log program the way c-abi.yml owns
the leaf crate.

Publishing stays owner ceremony: the runner never publishes. The owner
downloads the run artifacts, drops the `.node` into
ts/npm/linux-arm64/, verifies with the pack-time tarball proof, and
publishes with the standing runbook; PUBLISHING.md's 0.17.2 entry
spells exactly that flow, duty binary included for the example bundle.
