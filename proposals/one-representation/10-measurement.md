# 10 — Measurement: attribution before representation

The upstream report is explicit: *measure before choosing a transport; do
not select a representation from intuition alone*. This document is that
mandate made concrete. It adds the missing phase spans, defines the
Primer-shaped lane, fixes the report's component table as the output
format, and pins the decision gates that 20 and 30 consume. Nothing in 20
or 30 that depends on a gate may land before the gate has numbers.

## What exists (and is kept as the one attribution mechanism)

- **Commit-side spans** (`crates/bumbledb/src/obs/point.rs`): `COMMIT`,
  `COMMIT_NOOP`, `APPLY_DELETES`, `APPLY_INSERTS`, `JUDGMENT_SOURCE`,
  `JUDGMENT_TARGET`, `JUDGMENT_CAPACITIES`, `COUNTERS_FLUSH`,
  `LMDB_COMMIT`, `POINT_READ`, `DICT_RESOLVE`.
- **Builder admission telemetry**: the five phase quantities `A/I/R/F/J`
  (`AdmissionTelemetry`, `crates/bumbledb/src/storage/catalog/freeze.rs`).
- **The counting allocator** (`crates/bumbledb/src/alloc_counter.rs`):
  event and byte windows plus absolute live/peak-live, installed under the
  `alloc-counter` feature; already the memory-observability mechanism for
  the bench and the zero-warm-allocation gate.
- **The bench crate** (`crates/bumbledb-bench`): `writebench`,
  `corpus_gen`, `trace_out`, the lane/report machinery.

These are THE attribution mechanisms. No ad-hoc timers in product code, no
second tracing system, no printf profiling. A performance claim in this
proposal set cites a span, a window, or a lane report — nothing else.

## The missing spans (added by this doc)

The Node profile attributes everything blocked in a native call to the
bridge frame — 12,235 `commit` samples with no split, and the entire
accumulation side (6,142 `record` samples) dark. New points, following the
existing `point.rs` vocabulary and category scheme:

| Point | Category | Wraps | Count arg |
| --- | --- | --- | --- |
| `MARSHAL_FACTS` | Write | one bridge collection marshal (`fact_rows` today; the accepted-collection build after 20) | rows |
| `DYN_PARSE` | Write | `parse_dyn_collection` (dies with 20; span moves to the collection-view walk) | rows |
| `DYN_ENCODE` | Write | the intern+encode loop of one collection (`apply_collection`'s encode phase) | rows |
| `DELTA_APPLY` | Write | `apply_prepared`'s backend-apply loop | rows |
| `BUILDER_LOAD` | Write | one `HeapStage` collection load | rows |
| `INTERN_PROBE` | Write | aggregate per collection: dictionary probes issued / memo hits (two-arg event, not per-string spans — a per-string span would cost more than the probe) | probes, hits |
| `PUBLISH_COPY` | Storage | `Environment::publish` data copy | bytes |
| `PUBLISH_SYNC` | Storage | publish's durability boundary | — |

Rules: spans are sampled at collection granularity, never per fact or per
cell (a span that allocates or syscalls per cell would be V3 reborn as
instrumentation). The existing commit spans are not renamed — the split
the report asks for (judgment vs dictionary work vs index application vs
LMDB commit) already exists as `JUDGMENT_*` / `COUNTERS_FLUSH` /
`APPLY_INSERTS` / `LMDB_COMMIT`; what was missing is everything before the
commit and the publish split.

## The Primer-shaped lane

One new lane in `bumbledb-bench` (working name `primerlane`), generated by
`corpus_gen` with the shape the reports describe, checked in as a
generator config — never as a data file:

- ~4.0 M facts across 39 ordinary relations plus 3 closed relations;
  arities 2–8; every relation fresh-keyed; a containment graph and
  capacity statements at Primer's density (~123 statements).
- String columns with a Zipf-distributed vocabulary (the committed-repeat
  case 30 targets) and a long-tail novel population (the pending case),
  sized so the store and dictionary land near Primer's 1.68 GB shape.
- **Two write lanes, both measured** — they exercise different backends of
  the one `MutationCore` protocol:
  1. *builder lane*: `InstanceBuilder` load → `admit` → `Db::from_instance`
     (Primer's persist path; `HeapMutation`, then publish);
  2. *delta lane*: `db.write` + `tx.insert` against an existing store of
     the same corpus (the incremental path; `StoreMutation`, the
     per-fact committed-membership probe, the full commit pipeline).
- **Two read lanes**: full `scan` decode (the retired readback, kept as
  the regression baseline) and `count` per relation (after 40).
- Run under `alloc-counter`; each component below is one allocation
  window.

The TS-side components run the same corpus through the real bridge from a
harness under `ts/` (the package's own bench script, same generator
config). JS-side numbers derive from the native span tree by subtraction —
wall time of the one bridged call minus the root native span — never from
a second instrumentation system inside product code.

## The output: the report's component table, verbatim

Every lane run emits one table with exactly these rows (the upstream
report's required components), each with wall time, allocation events,
allocated bytes, and peak live:

1. TypeScript fact projection
2. JavaScript-to-native marshaling
3. native batch parsing
4. string ownership and interning
5. delta apply
6. commit judgment
7. dictionary flush
8. relation and determinant index application
9. LMDB commit
10. scan transport
11. fact decoding
12. exact count

Mapping: 1 = harness minus bridge root; 2 = `MARSHAL_FACTS`; 3 =
`DYN_PARSE`; 4 = `INTERN_PROBE` + the dictionary share of `DYN_ENCODE`;
5 = `DELTA_APPLY`/`BUILDER_LOAD`; 6 = `JUDGMENT_*`; 7 = `COUNTERS_FLUSH`
(dictionary puts + next-id); 8 = `APPLY_INSERTS`/`APPLY_DELETES` (M/F/U/R
puts) and, on the builder lane, the freeze emit phases; 9 = `LMDB_COMMIT`
(+ `PUBLISH_COPY`/`PUBLISH_SYNC` on the builder lane); 10–11 = the scan
read lane; 12 = the count read lane.

## The representation matrix (consumed by 20)

The lane runs the collection crossing in each candidate physical form,
same corpus, same laws:

| Candidate | Description |
| --- | --- |
| R0 (baseline) | today's nested rows: JS row arrays → `Vec<Vec<Value>>` → `ParsedRow` |
| R1 | flat row-major: one arity-strided cell sequence, no per-row containers on either side |
| R2 | arena-backed: R1 plus one string arena and one bytes arena; cells carry offsets ([30-string-ownership.md](30-string-ownership.md)) |
| R3 | columnar: one sequence per sealed field — built **only if** R1/R2 profiling shows a field-major access pattern worth it; otherwise recorded as refused with the numbers that refused it |

R0 is measured first and becomes the ledger baseline in
[70-deletions.md](70-deletions.md). Phase-1 waste removals (V3, V4 —
lazy error contexts, hoisted rosters) land *before* the matrix runs, on
R0, so the matrix measures representations, not noise.

## Decision gates

- **G1 (physical form, consumed by 20 — a refutation gate, not a
  selection ceremony):** the build target is pinned NOW: **R2**. The
  fleet builds R2 while this lane builds the rig; the matrix exists to
  refute the pin before merge, never to serialize the build behind a
  bake-off. The gate: R2 beats R0 on builder-lane end-to-end wall time
  AND on peak live bytes. Refuted ⇒ the 20/30 merge blocks and the pin is
  re-litigated here with the numbers; confirmed ⇒ merge. R1 and R3 are
  measured for the record; a candidate beating R2 materially (>10% on
  both axes) swaps the pin by one-line amendment before release, and R3
  is not built at all unless R1/R2 profiling shows a field-major access
  pattern.
- **G2 (committed-string memo, consumed by 30):** the delta lane with the
  memo must reduce component 4's wall time and LMDB get count with no
  regression elsewhere. If the corpus shows the memo table's live bytes
  exceeding its LMDB savings envelope, 30's memo is bounded (see 30) and
  the bound is pinned here.
- **G3 (type-tier wall budget, consumed by 60):** `tsc` on the law-scale
  suite (`ts/test/law-scale.test.ts` scale: ~40 relations, ~123
  statements) must not regress check time by more than 15% with the
  target-key wall enabled. Over budget → 60 ships value-tier only and
  records the ruling.
- **G4 (acceptance numbers, consumed by 80):** the lane's before/after
  table is the evidence attached to every acceptance condition; Primer's
  own `verify:learning-commons` run is the final gate, not a substitute
  for the lane.

## Consumers

20 and 30 (G1, G2), 60 (G3), 80 (G4), and Primer (the lane is the
regression harness that keeps the 27.61 s / 7.22 GiB class of drift from
returning unnoticed).
